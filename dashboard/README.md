# ФК — дашборд производства

Отдельный веб-сервис, который показывает аналитику по данным бота ФК.
Живёт на вашей ВМ (виртуальная машина), крутится в Docker, наружу смотрит через nginx.

## Главное про безопасность данных

Сервис **не пишет в базу и не может этого сделать**. Три уровня защиты:

1. Соединение открывается с `default_transaction_read_only=on` — PostgreSQL отбивает
   любой `INSERT/UPDATE/DELETE/CREATE/DROP/TRUNCATE` ошибкой `25006`.
2. В коде стоит guard `_assert_read_only()` — выполняются только `SELECT` и `WITH`.
3. В сервисе физически нет ни одного SQL-запроса на запись, нет миграций,
   нет `CREATE TABLE IF NOT EXISTS`. Только два `SELECT` (см. `sources.py`).

Плюс `statement_timeout` (по умолчанию 15 с), чтобы тяжёлый запрос не подвесил базу,
и кеш на стороне сервиса — в базу ходим раз в `CACHE_TTL` секунд независимо от
числа открытых вкладок.

Бот (`bot.py` в корне репозитория) не изменён ни на строку.

## Режимы источника данных (`SOURCE_MODE`)

| Режим  | Что делает | Когда нужен |
|--------|-----------|-------------|
| `db`   | Прямой коннект к PostgreSQL, только чтение | ВМ видит базу по сети (основной вариант) |
| `api`  | Тянет готовый `/api/dashboard/all` бота по ключу | База закрыта, но HTTP бота доступен |
| `demo` | Локальный `demo_data.json`, к базе не обращается | Проверить деплой и nginx, не трогая прод |

## Названия разделов

Переключатель сверху: **[ Формовочный цех ] [ Тестозаготовочный цех ] [ Печной цех ] [ Кондитерский цех ] [ Тайминги ]**.
Это прежние ФК, БХМ, Расстойка, КЦ и Гант: внутренние ключи (`?source=fk|bhm|proofing|kc|gantt`), API и имена
файлов выгрузок не менялись — старые ссылки работают. На узком экране кнопки встают сеткой 3 + 2.

## Второй источник: БХМ (тестозаготовочный цех)

Сверху страницы переключатель **[ ФК ] [ БХМ ]**. По умолчанию — ФК, выбор
запоминается в браузере (`localStorage`, ключ `fk_source`). Дашборд БХМ — та же
страница, те же графики, таблицы, сводка фактов, LFL, Excel и PDF, только объём
в **кг** и **кг/ч** вместо шт и шт/ч.

Как это устроено:

- Бот БХМ живёт в своём репозитории (`HR-analyze/FK_BHM`) и своей базе. Сюда не
  копируется ни строки его кода, базы не объединяются, submodule нет.
- Связь только по HTTP: бэкенд дашборда делает
  `GET {BHM_API_URL}/api/dashboard/all` с заголовком `X-API-Key: {BHM_API_KEY}`.
  Ключ живёт только в `.env` на сервере — в браузер, ответы API и логи он не попадает.
- `bhm_source.py` приводит ответ БХМ к тому же формату, что у ФК
  (`production` + `pauses`), дальше считают те же `aggregate.py` и `exports.py`.
- Снимок кешируется отдельно от ФК, тоже на `CACHE_TTL` секунд. Если API БХМ
  недоступен — ФК работает как обычно, а на БХМ видна ошибка.

Как операции БХМ ложатся на дашборд:

| БХМ | дашборд |
|-----|---------|
| `start_at` (по `TIMEZONE`) | дата, `created_at`, сравнение «до того же часа» |
| `start_time` / `end_time` | старт / финиш, длительность, смена, час |
| `user_name`, `equipment`, `product`, `status` | как есть (без оборудования — «Без оборудования») |
| `operation_name` | колонка «Операция» в детализации |
| `quantity_kg` | выпуск, **только у шага замеса** (см. ниже) |
| `status = skipped / cancelled` | не попадают: пропуск — не работа, отмена — не выпуск |

**Почему кг берутся только с замеса.** Вес партии вносят один раз, а бот БХМ
копирует его во все шаги партии (сборка, замес, отлежка, обминка, подача). Если
сложить `quantity_kg` всех шагов, одна партия посчитается 5–6 раз (на тестовых
данных — 72 067 кг вместо 14 146 кг). Поэтому объём даёт один шаг —
`BHM_VOLUME_OPERATION`, по умолчанию `dough_mixing` («Замешано», как в аналитике
самого БХМ). Остальные шаги идут операциями с длительностью и нулевым объёмом.
Следствия: «Выпуск по оборудованию» показывает кг только у Diosna, а средняя
производительность (кг/ч) — это производительность замеса.

Чего у БХМ нет: загрузки плана. Поэтому при БХМ вкладки «План / факт» и
«История загрузок» скрыты, а в Excel «всё» нет листа плана.

Фильтры у каждого источника свои: справочники берутся из выбранного источника,
а при переключении ФК ↔ БХМ фильтры каждого сохраняются отдельно (в пределах
открытой вкладки браузера).

Переменные (`.env`):

```ini
BHM_API_URL=https://<хост БХМ>
BHM_API_KEY=<DASHBOARD_API_KEY из .env бота БХМ>
# необязательные
BHM_SOURCE_MODE=          # api | demo | off; по умолчанию сам выбирает по BHM_API_URL / SOURCE_MODE
BHM_VOLUME_OPERATION=dough_mixing
BHM_EXCLUDE_DATES=        # скрытые даты только для БХМ (EXCLUDE_DATES действует только на ФК)
```

Без `BHM_API_URL` кнопка «БХМ» неактивна. В `SOURCE_MODE=demo` БХМ читает
`bhm_demo_data.json` — это ответ API в том же формате, что отдаёт бот.

Проверка связи с ВМ дашборда:

```bash
curl -s -o /dev/null -w "%{http_code}\n" -H "X-API-Key: $BHM_API_KEY" "$BHM_API_URL/api/dashboard/all?date_from=$(date +%F)"
# 200 — всё ок, 401 — ключ не тот (или DASHBOARD_API_KEY у бота пуст)
curl -s "localhost:8090/api/meta?source=bhm" | head -c 300
```

## Третий источник: Расстойка и отпекание

Переключатель сверху — **[ ФК ] [ БХМ ] [ Расстойка ]**. Раздел «Расстойка» —
аналитика бота [`HR-analyze/rastoyka_fk`](https://github.com/HR-analyze/rastoyka_fk):
изделие проходит расстойку, затем отпекание в одной из печей (подовая — поды,
ротационная и термомасляная — шпильки).

Как устроено:

- Только HTTP: `proofing_source.py` делает `GET {PROOFING_API_URL}/api/dashboard/all`
  с заголовком `X-API-Key: {PROOFING_API_KEY}` (= `DASHBOARD_API_KEY` бота расстойки).
  К базе бота дашборд не подключается, его таблицы никуда не копируются, своей
  базы под расстойку нет — снимок живёт в памяти и кешируется на `CACHE_TTL`.
- `ANALYTICS_KEY` бота (экран «Аналитика» в Mini App) **не используется** — это ключ для людей.
- Расчёты — `proofing_aggregate.py`, выгрузки — `proofing_exports.py`. Общие
  `aggregate.py` / `exports.py` ФК и БХМ не менялись: у расстойки партия из двух
  этапов, плоская модель «операция = выпуск» для неё неверна.
- Если API расстойки недоступен, ошибка видна **только** в разделе «Расстойка»
  (с кнопкой «Повторить»), ФК и БХМ работают, `/health` не падает.

Вкладки раздела: **Сводка** (KPI, графики, таблицы) и **Партии** (подробная
таблица партий с поиском и галереей фото).

### Правила расчёта

| Показатель | Как считается |
|---|---|
| Начато партий | по времени начала расстойки; отменённые входят и показаны отдельно |
| Завершено / выпуск, шт | по времени **конца отпекания**: `pieces_end` закрытого отпекания, ровно один раз на партию; `pieces_out` партии — только сверка |
| Отменённые партии | не попадают в выпуск, длительности, шт/ч и загрузку |
| В работе | на конец периода: начаты до него и не завершены/не отменены к нему |
| Длительность этапа | `end_at − start_at` (время с поясом, переход через полночь учтён); в средние — только корректно закрытые (0 < t ≤ `PROOFING_MAX_STAGE_HOURS`) |
| шт/ч отпекания | Σ выход / Σ часов отпекания по партиям с корректным отпеканием (не среднее средних); нет данных — «Нет данных», деления на ноль нет |
| Выпуск по часам | по часу окончания отпекания |
| Загрузка оборудования | объединение интервалов этапов: две партии в печи одновременно — 1 ч занятости, а не 2; отдельно видно «сумма по партиям» и «одновременно до N» |
| Поды и шпильки | никогда не складываются: загрузка показывается в единице каждой печи |
| Незакрытые этапы | отдельная таблица; дольше лимита — с ⚠ |

Фильтры: период, изделие, оборудование, тип печи, сотрудник, смена, час, статус
партии. Период, смена и час применяются к **времени события** (старт — к началу
расстойки, выпуск — к концу отпекания и т. д.). Сотрудник — любая его отметка в
партии: начать расстойку и закрыть отпекание могут разные люди, в таблице
«Сотрудники по отметкам» видно, кто что делал. У критических остановок нет изделия
и партии, поэтому фильтры изделия и статуса их не сужают. Тепловая карта загрузки
при фильтре часа/смены подсвечивает нужные часы, а не пересчитывается.

Сравнение с прошлым периодом — тот же отрезок прямо перед текущим с теми же
фильтрами (если период заканчивается сегодня — до того же времени суток), по
дням — тот же день неделей раньше.

Фото: в таблице партий кнопка «📷 N» открывает галерею. Картинки грузятся только
по нажатию через `GET /api/proofing/photo/{id}` дашборда: сервер сам ходит в
`/api/dashboard/photo/{id}` бота с ключом в заголовке, браузер ключа не видит.
Отдаются только фото из текущего снимка (не открытый прокси), не больше 4
запросов к боту одновременно, последние фото кешируются в памяти.

Плана у расстойки нет: планы ФК в неё не переносятся, вкладки «План / факт»
скрыты, пока не появится согласованный источник планов расстойки.

Переменные (`.env`):

```ini
PROOFING_SOURCE_MODE=api            # api | demo | off; без значения: есть URL — api
PROOFING_API_URL=https://<хост бота расстойки>   # без /api/dashboard/all
PROOFING_API_KEY=<DASHBOARD_API_KEY из .env бота расстойки>
# необязательные
PROOFING_TIMEOUT=30                 # таймаут запроса данных, с
PROOFING_PHOTO_TIMEOUT=20           # таймаут запроса фото, с
PROOFING_MAX_STAGE_HOURS=18         # этап длиннее — некорректный (как MAX_OPERATION_HOURS бота)
PROOFING_EXCLUDE_DATES=             # скрытые даты только для расстойки
PROOFING_PHOTO_CACHE_ITEMS=64
PROOFING_PHOTO_CACHE_MB=48
```

Проверка связи:

```bash
curl -s -o /dev/null -w "%{http_code}\n" -H "X-API-Key: $PROOFING_API_KEY" "$PROOFING_API_URL/api/dashboard/all?date_from=$(date +%F)"
curl -s -u "$DASHBOARD_USER:$DASHBOARD_PASSWORD" "localhost:8090/api/meta?source=proofing" | head -c 300
```

В `SOURCE_MODE=demo` раздел читает `proofing_demo_data.json` — ответ API в формате
бота (генератор: `dashboard/tests/make_proofing_demo.py`).

## Четвёртый источник: КЦ — кондитерский цех

Переключатель сверху — **[ ФК ] [ БХМ ] [ Расстойка ] [ КЦ ]**. Раздел «КЦ» — аналитика бота
[`HR-analyze/fk_conditerka`](https://github.com/HR-analyze/fk_conditerka). Вкладки:
**Сводка** (KPI, графики, трудозатраты, сотрудники, остановки), **Операции** (подробная
таблица с поиском и сортировкой), **Нормативы** (пары «продукция + операция»).

Как устроено:

- Только HTTP: `kc_source.py` делает `GET {KC_API_URL}/api/dashboard/all` с заголовком
  `X-API-Key: {KC_API_KEY}` (= `DASHBOARD_API_KEY` бота КЦ, **не** `ANALYTICS_KEY`).
  К базе бота дашборд не подключается, своей базы под КЦ нет — снимок в памяти на `CACHE_TTL`.
- Поля API — ровно те, что закреплены тестом бота `test_dashboard_all_contract`
  (`operations[]`: `id, product, operation, people, quantity_pcs, start_*, end_*, status, user_*,
  closed_by_*, created_at, closed_at` + посчитанные ботом метрики; `pauses[]`: причина и время).
  Длительность, чел·ч и выработку дашборд пересчитывает сам по `start_at`/`end_at` (с минутами
  точнее, чем целые минуты бота) — одна формула для страницы, Excel и PDF.
- Расчёты — `kc_aggregate.py`, выгрузки — `kc_exports.py`; общие модули ФК/БХМ и расстойки не менялись
  (КЦ берёт из `proofing_aggregate.py` только общее окно периода/смены и форматирование).
- Бот фильтрует по `start_at`, а завершённая работа считается по `end_at`. Снимок берётся за
  `MAX_DAYS` **+ 1 сутки** и фильтруется на стороне дашборда: операция, начатая до периода и
  закрытая внутри него, попадает в период (бот не меняется).
- API КЦ недоступен — ошибка только в разделе «КЦ» (кнопка «Повторить»); ФК, БХМ и расстойка
  работают, `/health` не падает.

### Правила расчёта

| Показатель | Как считается |
|---|---|
| **Обработано изделий по операциям, шт** | Σ `quantity_pcs` завершённых операций. **Не готовый выпуск**: ромовая баба 600 шт × (накалывание, купание, декорирование) = 1 800 «обработано», а изделий 600. Предупреждение есть на странице, в Excel и PDF |
| Завершено / в работе / отменено | раздельно: завершённые — по времени конца, начатые и отменённые — по началу, «в работе» — на конец периода |
| Человеко-часы | длительность, ч × `people` |
| шт/ч, шт/чел·ч операции | шт / ч, шт / чел·ч |
| Средняя выработка группы | Σ шт / Σ чел·ч (не среднее коэффициентов); по всему цеху — с предупреждением о смешении операций |
| Средние, мин – макс, нормы | только корректно закрытые операции (0 < t ≤ `KC_MAX_OPERATION_HOURS`) |
| Нормативы | по паре «продукция + операция»: выполнения, шт, ср./мин/макс время, ср. людей, чел·ч, шт/ч, шт/чел·ч и изменение шт/чел·ч к прошлому периоду. Это **наблюдаемые** значения, а не утверждённый норматив |
| Сотрудники | кто начал / завершил / отменил и активность по часам. `people` — численность группы, поэтому выработка конкретным людям не приписывается; «шт в завершённых им» — штуки группы |
| Смены | день 08–20, ночь 20–08; работа через полночь считается по реальному времени, ночная смена относится к дате её начала (таблица «По сменам», значок 🌙) |
| Остановки | количество, длительность по `start_at`/`end_at`, причины, динамика по дням, журнал |

Фильтры: период, продукция, операция, сотрудник (начал или завершил), смена, час, статус. Период,
смена и час применяются к времени события. У остановки нет продукции/операции/статуса — эти
фильтры её не сужают. План-факт в КЦ не показывается: источника планов КЦ нет.

Переменные (`.env`):

```ini
KC_SOURCE_MODE=api            # api | demo | off; без значения: есть URL — api
KC_API_URL=https://<хост бота КЦ>   # без /api/dashboard/all
KC_API_KEY=<DASHBOARD_API_KEY из .env бота КЦ>
# необязательные
KC_TIMEOUT=30                 # таймаут запроса, с
KC_MAX_OPERATION_HOURS=18     # операция длиннее — некорректная (как MAX_OPERATION_HOURS бота)
KC_EXCLUDE_DATES=             # скрытые даты только для КЦ
```

Проверка связи:

```bash
curl -s -o /dev/null -w "%{http_code}\n" -H "X-API-Key: $KC_API_KEY" "$KC_API_URL/api/dashboard/all?date_from=$(date +%F)"
curl -s -u "$DASHBOARD_USER:$DASHBOARD_PASSWORD" "localhost:8090/api/meta?source=kc" | head -c 300
```

В `SOURCE_MODE=demo` раздел читает `kc_demo_data.json` (генератор: `dashboard/tests/make_kc_demo.py`).

## Пятый раздел: «Тайминги» (Гант) — все цеха на одной шкале и общий тайминг

Переключатель — **[ ФК ] [ БХМ ] [ Расстойка ] [ КЦ ] [ Гант ]**. «Гант» не отдельный бот, а
сводка уже подключённых цехов (`gantt.py`, выгрузки — `gantt_exports.py`). Вкладки:

- **Диаграмма Ганта** — рабочие сутки и окно (сутки 08–08, день 08–20, ночь 20–08, календарные
  00–24), цеха кнопками, продукт, оборудование, поиск. Строки: **цех → продукт → его операции**.
  Продукты **по умолчанию свёрнуты** (видна строка продукта с его операциями тонкой полосой);
  нажми на продукт — развернутся операции, есть «Развернуть все» / «Свернуть все». Если выбран
  один продукт или идёт поиск, найденное разворачивается само. После названия — колонки **Оборудование · Людей ·
  Выработка в час на человека**; в строке продукта его операции тонкой полосой. Полоса — операция;
  на полосе и в подсказке: люди · выработка · оборудование, длительность, шт/ч и шт/чел·ч.
  Параллельные операции одной строки — на отдельных дорожках. Тап по полосе — подробности под
  диаграммой (на телефоне колонки уходят строкой под название). Пунктир — границы смен, красная — «сейчас».
  - «Людей» у операции — сколько было на запуске (максимум); у продукта — **максимум одновременно
    занятых** (имён нет, сумма по операциям посчитала бы человека дважды; сумма — в подсказке).
  - «Выработка в час на человека» у операции = Σшт / Σчел·ч по закрытым операциям. Где людей бот
    не знает (тестозаготовочный, формовочный, печной цеха) — бледным «в час на всех».
  - У продукта — **выработка продукта**, как в «Среднем по продукту»: количество последнего этапа
    (самая массовая операция; операции не складываются — одни и те же изделия проходят их все) /
    чел·ч всех операций продукта; без людей — / время **закрытых** операций продукта в окне.
    Незакрытая операция («идёт», например забытая с утра «Сборка теста») в это время не входит —
    иначе она раздувает время до «сейчас». В подписи продукта — «не закрыто N».
    Откуда количество — в подсказке. «—» — в окне нет закрытой операции с количеством.
  - «Занято» — время работы внутри выбранного окна без пауз между запусками.
- **Общий тайминг** — путь продукта **БХМ → формовка → расстойка → отпекание → КЦ → фасовка**: для
  каждого продукта начало/конец этапа, длительность, выработка, люди, ожидание между этапами и
  время от первого начала до последнего конца. На диаграмме — реальные операции каждого этапа.
- **Среднее по продукту** — средний день продукта за период «Среднее с … по …» (по умолчанию
  последние 7 рабочих суток). Для каждого продукта: дней с данными, весь путь в среднем (и
  разброс от–до), **выработка продукта в день и на чел·ч**, чел·ч в день, этапы с длительностью.
  Выработка продукта — количество на последнем этапе с количеством (ближе всего к готовой
  продукции; единица по приоритету шт → пласт/лист → кг, замес/форма/кольцо — не продукция), внутри
  этапа — самая массовая операция. Операции **не складываются**: одни и те же изделия проходят
  несколько операций. На чел·ч — эти штуки / человеко-часы всех операций продукта (где люди известны). Продукт разворачивается: диаграмма
  «от старта продукта» (+1ч, +2ч…) по этапам и операциям и таблица — начало от старта, длится
  (от первого начала до последнего конца), занято, людей в среднем, выработка в день, шт/чел·ч,
  оборудование. Каждые рабочие сутки (08–08) продукта — один «прогон», затем среднее по дням.
- **Справочник продуктов** — соответствия названий цехов единому продукту и операций — единой
  операции (см. ниже).

Цеха в «Таймингах» называются так же, как разделы: тестозаготовочный, формовочный, печной (этапы
«расстойка» и «отпекание»), кондитерский. В справочнике принимаются и старые названия (БХМ, ФК,
Формовка, Расстойка, КЦ).

Откуда данные:

| Цех | Операция на шкале | Люди | Выработка |
|---|---|---|---|
| БХМ | шаг партии (сборка, замес, отлежка…) | нет данных | кг (только замес, как в разделе БХМ) |
| Формовка (бот ФК) | формовка на линии | нет данных | шт |
| Расстойка | расстойка и отпекание партии | нет данных | шт на входе / выход после печи |
| КЦ | операция бота | `people` | шт |
| КЦ, чат 06–12.10 | разобранный чат Telegram | из сообщения | шт / кг / пласты / замесы — как написано |

Правила: время по `TIMEZONE`, операции через полночь не режутся; в окно попадает операция,
пересекающая его хоть минутой; у бота операция без конца — идёт (до «сейчас»), у чата — конец не
отмечен (ромб, без длительности). Единицы не складываются. Если один из цехов недоступен, Гант
строится по остальным и пишет, чего нет.

**Чат КЦ.** Пока бот КЦ не запущен в цехе, тайминги писали в чат. Он разобран один раз
(`dashboard/tests/build_kc_chat_history.py` → `kc_chat_history.json`) по сменам: каждая смена —
извлечение и независимая перепроверка по тексту, затем сверка стыков смен. У каждой операции —
номера исходных сообщений. Время из текста — точное; «~» — время самого сообщения («Закончили»,
«Заказ отдали» без времени); «≈» — выведено из контекста при явном основании (та же бригада
перешла на другую операцию, начат следующий этап того же продукта). «~» и «≈» помечены
«проверить» (штриховка), основание — в примечании. Заведомо неверное время (мастер сам написал,
что тайминг некорректен) — «некорректно», в шт/ч не идёт. Синонимы операций сведены к одному
названию («Набивка», «Начинка» → «Внесение начинки», «Прокол шпажкой» → «Прокол»), как было в
переписке — в примечании; названия продуктов не склеиваются (это решает цех справочником).
Тексты сообщений и имена в репозиторий не попали. Плюс отметки «сдано / передано на фасовку».
Эти данные идут только в «Тайминги», раздел «Кондитерский цех» по-прежнему считает только бота.

**Данные КЦ из переписки неточные** — это написано на странице (жёлтая плашка на всех вкладках
Ганта, «из переписки, неточно» у строк и продуктов), в Excel (колонка «Источник») и в PDF. Время —
по сообщениям (часто время отправки, а не начала/конца), людей и количество писали не всегда:
для общей картины, не для норм.

**Общий тайминг связывает цеха по единому продукту, а не по номеру партии** — общего номера у
ботов нет. Названия у цехов разные («Батон / ромашка» в БХМ, «Батон классический» на формовке), а
в КЦ операции вводят руками («Начинка», «Внесение начинки», «Набивка начинкой»), поэтому есть
справочник: «Скачать шаблон Excel» → лист **«Соответствия»** (колонка «Единый продукт») и лист
**«Операции»** (колонка «Единая операция», видно, у каких продуктов встречается) → «Загрузить
справочник» с ключом `PLAN_UPLOAD_TOKEN`. Регистр, «ё», пробелы и знаки препинания сводятся
автоматически (к самому частому написанию). Похожие названия (опечатки, «фреш») только
**подсказываются** в колонке «Похоже на» и на вкладке — склеивать или нет, решает человек.
Старые файлы (только продукты, цех «ФК») загружаются как раньше. Хранится в PostgreSQL дашборда
в отдельной таблице `fk_dashboard_product_map` (планы и история загрузок не затрагиваются); без
PostgreSQL — файл `product_map.json` рядом с `PLAN_FILE`.

**Фасовка** — будет отдельным ботом; этап в тайминге уже заложен («нет источника»), пока видны
только отметки «передано на фасовку» из чата КЦ.

API: `GET /api/meta?source=gantt`, `GET /api/summary?source=gantt&date=YYYY-MM-DD&window=full|day|night|calendar&sections=bhm,fk,proofing,kc&product=&equipment=&avg_from=YYYY-MM-DD&avg_to=YYYY-MM-DD`,
`GET /api/gantt/map`, `GET /api/gantt/map/template`, `POST /api/gantt/map/upload` (`X-Plan-Token`),
выгрузки `GET /api/export/xlsx|pdf?source=gantt&…`.

**Выгрузки процессов** (за период «Среднее с … по …», как вкладка «Среднее по продукту»):

- **Excel** — сначала плоские листы для фильтров и сводных таблиц, время числом в формате `ч:мм`:
  «Процессы по цехам» (строка — цех · этап цеха · продукт · операция: шаг, дней, начало от старта
  продукта, длится, занято, людей, выработка в день числом + ед., в час, в час на человека,
  оборудование, источник) — фильтр «Цех» собирает все процессы цеха; «Цеха · операции» (свод по
  цеху: операция, у каких продуктов, сколько длится — среднее, минимум, максимум); «Продукты
  (среднее)»; «Этапы по продуктам». Затем — выбранные сутки: строки диаграммы, операции, общий
  тайминг, передано на фасовку, справочники, фильтры.
- **PDF** — сводка, затем раздел «Процессы по продуктам»: таблица всех продуктов и **блок на каждый
  продукт** — цеха, дни, весь путь, выработка, средний день на шкале «от старта продукта» (этапы и
  операции) и таблица этапов и операций с началом, длительностью, занятостью, людьми, выработкой и
  оборудованием. Файл большой (десятки страниц) — так задумано. Дальше — диаграмма выбранных суток,
  общий тайминг и операции.

Тесты — `python3 dashboard/tests/test_gantt.py`.

## Деплой на ВМ

### 0. Что должно быть на машине

```bash
docker --version && docker compose version   # Docker и плагин compose
nginx -v                                     # nginx
```

Если Docker не стоит (Ubuntu/Debian):

```bash
curl -fsSL https://get.docker.com | sh
sudo apt-get install -y nginx
```

### 1. Забрать код

```bash
sudo mkdir -p /opt && cd /opt
sudo git clone https://github.com/HR-analyze/fk_analiz.git
cd /opt/fk_analiz/dashboard
```

### 2. Настроить `.env`

```bash
cp .env.example .env
nano .env
```

Минимум, что надо заполнить для боевого режима:

```ini
SOURCE_MODE=db
DATABASE_URL=postgresql://USER:PASSWORD@HOST:5432/DBNAME?sslmode=require
TIMEZONE=Europe/Moscow
CACHE_TTL=60
REFRESH_SECONDS=60
EXCLUDE_DATES=2026-09-01
PLAN_UPLOAD_TOKEN=<длинная случайная строка>
```

`DATABASE_URL` — та же строка подключения, что у бота на Relax Dev.
Если панель отдаёт хост/порт/юзера по отдельности, строка собирается так:
`postgresql://<user>:<password>@<host>:<port>/<database>?sslmode=require`.

> Если база на Relax Dev слушает только внутреннюю сеть — прямого коннекта с ВМ не будет.
> Тогда переключись на `SOURCE_MODE=api`, укажи `BOT_API_URL` и `BOT_API_KEY`
> (тот же `DASHBOARD_API_KEY`, что задан у бота).

### 3. Сначала прогнать на демо-данных

Чтобы убедиться, что контейнер и nginx живые, ещё не подключаясь к боевой базе:

```bash
SOURCE_MODE=demo docker compose up -d --build
curl -s localhost:8090/health
```

Ожидаем `{"ok": true, "mode": "demo", ...}`.

### 4. Переключить на боевые данные

```bash
docker compose down
docker compose up -d --build        # теперь читает SOURCE_MODE из .env
docker compose logs -f --tail=50
```

В логах должно быть:
`snapshot refreshed: production=… pauses=… mode=db`

### 5. nginx

```bash
sudo cp nginx/rate-limit.conf /etc/nginx/conf.d/fk-dashboard-rate-limit.conf
sudo cp nginx/fk-dashboard.conf /etc/nginx/sites-available/fk-dashboard.conf
sudo nano /etc/nginx/sites-available/fk-dashboard.conf   # подставить свой server_name
sudo ln -s /etc/nginx/sites-available/fk-dashboard.conf /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
```

Проверка: `curl -I http://<домен-или-IP>/` → `200 OK`.

### 6. HTTPS (если есть домен)

```bash
sudo apt-get install -y certbot python3-certbot-nginx
sudo certbot --nginx -d dashboard.example.ru
```

### 7. Файрвол

Наружу нужны только 80/443. Порт 8090 слушает **только localhost** (см. `docker-compose.yml`),
поэтому мимо nginx к сервису не достучаться.

```bash
sudo ufw allow 80,443/tcp && sudo ufw enable
```

## Что показывает дашборд

Фильтры: период (даты от/до), оборудование, продукт, **сотрудник**, смена
(день 08:00–20:00 / ночь 20:00–08:00) и **час суток**. Фильтры комбинируются.

- 6 KPI: операций, выпуск (шт), средняя длительность, средняя производительность,
  число простоев, коэффициент использования = работа / (работа + простои);
  у каждого — изменение к прошлому периоду (см. «Сравнение с прошлым периодом»)
- Выпуск по дням, производительность по часам (штуки распределяются по минутам операции)
- Выпуск по оборудованию, топ продуктов, **выпуск по сотрудникам**
- Простои по причинам (круговая), работа vs простои (кольцевая)
- Сводка фактов — текстовая выжимка, она же попадает в PDF
- Сводка по дням карточками: выпуск крупно, доля от лучшего дня полоской,
  план с процентом выполнения, операции, средняя длительность и простои
- **Сводка по сотрудникам**, сводка по оборудованию, тайминги по продуктам,
  **план/факт по позициям**, детализация операций

### Сравнение с прошлым периодом (LFL)

LFL (like-for-like — «сравнение как с как») отвечает на вопрос «становится лучше или нет».
Везде сравнение идёт **с теми же фильтрами** (оборудование, продукт, сотрудник, смена, час).

| Где | С чем сравниваем |
|---|---|
| KPI-плитки | с прошлым периодом той же длины вплотную перед текущим; при недельном периоде по умолчанию — неделя к неделе |
| Выпуск по дням, светлый столбец за синим | каждый день — с тем же днём недели неделей раньше |
| Выпуск по дням, полоски «Неделя к неделе» | до 8 недель, выровненных по концу периода, свежая сверху: длина полосы — выпуск, рядом изменение к неделе раньше и число простоев; недели без данных не показываются |
| Производительность по часам, блок под графиком | две ячейки — средняя и часов ниже средней (было/стало), и полоса из 24 клеток: каждый час к тому же часу прошлого периода в % |

На «Выпуске по дням» сравнение нарисовано «столбцом в столбце»: широкий светлый — было,
узкий цветной поверх — стало. Цветной торчит выше светлого — выросли, ниже — просели.
Сам часовой график сравнением не нагружен (на нём уже средняя и красные часы):
лучше/хуже по часам показывает полоса — зелёная клетка лучше, красная хуже,
ярче — больше 10%. На телефоне полоса в два ряда по 12 часов. Под каждым графиком легенда.

Цвет: зелёный — стало лучше, красный — хуже, серый — без оценки. Рост выпуска,
производительности и коэффициента использования — лучше; рост числа простоев — хуже.
Средняя длительность и число операций не оцениваются: дольше операция — не значит хуже,
это зависит от размера партии. Коэффициент использования сравнивается в **п.п.**
(процентных пунктах): 95,4% против 96,0% — это −0,6 п.п., а не «−0,6%».

**Неполный сегодняшний день.** Если период заканчивается сегодня, у дня, с которым
сравниваем, берутся только записи до того же времени суток (в подписи «до 12:45»).
Иначе утром любой период «проседает» только потому, что день не доработан.

**Неравное число дней.** Скрытые даты (`EXCLUDE_DATES`) и дни без записей делают суммы
несопоставимыми. Тогда под KPI и на карточке недели появляется ⚠ с числом дней —
смотри в первую очередь на производительность и коэффициент, они от числа дней не зависят.

Сравнение попадает в «Сводку фактов», PDF и Excel: в листы KPI, «Выпуск по дням»,
«Производительность по часам» добавлены колонки прошлого периода, плюс отдельный
лист «Неделя к неделе» (`widget=weekly`).

### Клик по графику = фильтр

Столбцы графиков, карточки дней и строки таблиц кликабельны: нажатие применяет
соответствующий фильтр, повторное нажатие по тому же значению — снимает его.
Активные фильтры показаны чипами под панелью фильтров, каждый снимается крестиком,
`Сбросить всё` возвращает период по умолчанию.

Зона нажатия шире самого столбца (вся колонка графика) — на телефоне попадать пальцем
не нужно точно в столбик.

### Вкладки

Страница разделена на три вкладки, выбранная запоминается в адресе (`#plan`)
и переживает перезагрузку:

| Вкладка | Что внутри |
|---|---|
| **Дашборд** | KPI, все графики, сводка фактов, сводки и детализация |
| **План / факт** | загрузка плана, плитки план/факт, таблица по позициям |
| **История загрузок** | журнал: когда, какой файл, на какие даты, сколько позиций, результат |

Фильтры общие для первых двух вкладок; на вкладке журнала они скрыты — там они
только сбивают с толку.

### План / факт

Панель под фильтрами показывает План, Факт, Выполнение и Недобор по позициям,
ниже — таблица «План / факт по позициям» с сортировкой по величине отставания.

Файл плана — рабочий шаблон Excel. Читаются четыре колонки, находятся по заголовку:

| Колонка шаблона | Что берём |
|---|---|
| `Сокращенное название` | продукт (совпадает с названием в базе бота) |
| `Оборудование` | линия |
| `План количество` | план в штуках; пустые и нулевые строки пропускаются |
| `Дата план` | дата плана |

⚠️ В шаблоне `Дата план` — формула `=$H$1`, а `H1` — `=TODAY()`. Если Excel не
сохранил вычисленное значение, дата приходит пустой. Поэтому рядом с кнопкой
загрузки есть поле **Дата плана** — она подставляется во все строки без даты.
Проверяй её перед загрузкой.

Планы накапливаются: повторная загрузка перезаписывает только те даты, что
пришли в файле. Хранятся в `PLAN_FILE` (по умолчанию `/app/data/plans.json`),
каталог примонтирован томом — переживает пересборку контейнера.
**База бота при этом не используется вообще.**

Файл можно **перетащить мышью** в зону загрузки или нажать на неё и выбрать в
проводнике. Каждая попытка — и удачная, и отклонённая — попадает в журнал на
вкладке «История загрузок» вместе с причиной отказа, так что видно, почему плана нет.

Загрузка защищена отдельным ключом, потому что сам дашборд публичный:

```ini
PLAN_UPLOAD_TOKEN=$(openssl rand -hex 24)
```

Пока ключ пустой, кнопка загрузки выключена и `POST /api/plan/upload` отдаёт 403.
Ключ спрашивается один раз и запоминается в браузере.

⚠️ **План разрезается только по дате, оборудованию и продукту** — других колонок
в файле нет. Фильтры по сотруднику, смене и часу сужают факт, но не план, поэтому
процент выполнения падает не потому, что не сделали, а потому, что сравнивается
часть с целым. В этом случае плитка называется «Доля от полного плана», а над
плитками появляется предупреждение. Для честного сравнения сними такой фильтр.

Недобор считается **по отстающим позициям**, а не как общее сальдо:
перевыполнение по одной номенклатуре не закрывает провал по другой.
Если план загружен не на все дни периода, под заголовком появляется
предупреждение — иначе сравнение вводит в заблуждение.

### Выгрузки

**Excel по виджету.** У каждой панели в шапке кнопка `⤓ Excel` — выгружает данные
именно этого графика или таблицы **с текущими фильтрами**. Кликнул по столбцу →
фильтр применился → нажал выгрузку → в файле только отфильтрованные данные.
Отдельный лист «Фильтры» фиксирует, что было применено и когда,
а имя файла содержит период и фильтры: `fk_detail_2026-09-02_2026-09-08_Glimek.xlsx`.

Кнопка `Excel: всё` в шапке страницы кладёт все виджеты листами в одну книгу.

**PDF всей сводки.** Кнопка `Скачать PDF` собирает документ: KPI, сводку фактов,
все графики (включая линию средней по часам), план/факт и таблицы. Файл строится
на сервере через reportlab, кириллица — шрифтом DejaVu, поэтому образ ставит
`fonts-dejavu-core`.

**Сводка фактов** — блок на странице и в PDF: итоги, дни с максимумом и минимумом,
топы по продуктам, оборудованию и сотрудникам, часы ниже средней, простои по
причинам, отставания по плану. Только числа и доли: причины простоя названы ровно
так, как их записал бот, без домыслов о том, что за ними стоит, и без рекомендаций.

### Провалы по часам

На графике «Производительность по часам» пунктиром отмечена средняя за период.
Часы ниже неё окрашены красным, их количество — в ячейке «Часов ниже средней»
под графиком, рядом с тем, сколько их было в прошлом периоде.

### Скрытие отдельных дат

Переменная `EXCLUDE_DATES` (через запятую, формат `YYYY-MM-DD`) убирает дни из отчёта:
они не попадают ни в KPI, ни в графики, ни в справочники, ни в детализацию.
**База при этом не меняется** — записи остаются на месте, фильтр работает только на чтении.
Убери дату из списка и перезапусти контейнер, чтобы она снова появилась.

```ini
EXCLUDE_DATES=2026-09-01
```

### Мобильная версия

- Панель фильтров свёрнута, в заголовке видно, какие фильтры активны
- KPI в две колонки, графики с укрупнёнными подписями (часть подписей прореживается)
- Таблицы превращаются в карточки «поле → значение» — горизонтального скролла нет
- Все нажимаемые элементы не меньше 44px
- Нажатия обрабатываются через `pointerup`, а не `click`: в мобильных браузерах
  `click` с не-интерактивных элементов (SVG-столбцы, строки таблицы) доходит до
  обработчика не всегда. Движение пальца больше 12px считается скроллом, а не нажатием

Страница сама обновляется каждые `REFRESH_SECONDS` секунд, в базу при этом ходит
не чаще `CACHE_TTL`. Графики нарисованы на чистом SVG — внешние CDN не нужны,
дашборд работает и в закрытом контуре без интернета.

## API сервиса

| Метод | Назначение |
|-------|-----------|
| `GET /` | сама страница |
| `GET /health` | 200 пока сервис может отдать данные, 503 если снимка нет |
| `GET /api/meta?source=fk\|bhm\|proofing\|kc` | справочники, границы дат, режим источника, единицы |
| `GET /api/summary?source=&date_from=&date_to=&equipment=&product=&employee=&shift=&hour=&refresh=1` | все показатели |
| `GET /api/plan` | что загружено: даты, число позиций, включена ли загрузка |
| `GET /api/plan/history` | журнал загрузок, свежие сверху |
| `POST /api/plan/upload` | загрузка xlsx (multipart `file`, опционально `date`), нужен `X-Plan-Token` |
| `DELETE /api/plan?dates=YYYY-MM-DD,...` | удалить планы на даты, нужен `X-Plan-Token` |
| `GET /api/export/xlsx?source=&widget=<виджет|all>&<те же фильтры>` | выгрузка виджета в Excel |
| `GET /api/export/pdf?source=&<те же фильтры>` | вся сводка в PDF |
| `GET /api/proofing/photo/{id}` | фото партии расстойки (прокси к боту, ключ остаётся на сервере) |

`source` — `fk` (по умолчанию, если не передан), `bhm`, `proofing` или `kc`. Неизвестный
источник — 400, БХМ, расстойка или КЦ без настроек или с недоступным API — 503 с текстом
ошибки. План (`/api/plan*`, `widget=plan`) — только у ФК.

У расстойки дополнительно фильтры `oven=hearth|rotary|thermal_oil` и
`status=active|done|cancelled`, виджеты: `kpi`, `daily`, `hourly`, `ovens`, `products`,
`employees`, `load_summary`, `load`, `reasons`, `pauses`, `open_stages`, `batches`, `all`.

У КЦ дополнительно фильтры `operation=<название>` и `status=closed|open|cancelled`, виджеты:
`kpi`, `daily`, `hourly`, `products`, `operations`, `norms`, `shifts`, `employees`, `activity`,
`reasons`, `pauses`, `open_ops`, `ops`, `all`.

Виджеты для `widget=`: `kpi`, `daily`, `weekly`, `hourly`, `equipment`, `products`,
`employees`, `reasons`, `work_vs_stop`, `plan`, `employee_timings`,
`equipment_timings`, `product_timings`, `detail`, либо `all` — все листами.

## Проверка вёрстки

`dashboard/tests/layout_check.py` прогоняет страницу по семи типовым разрешениям
на всех трёх вкладках и дополнительно прочёсывает ширины 320–1920px с шагом 40px.
Ловит четыре вида поломок: боковой скролл страницы, обрезанный текст, перенос
значения на вторую строку там, где оно должно быть в одну, и нажимаемые элементы
мельче норматива (44px на телефоне, 32px на десктопе).

```bash
pip install playwright && playwright install chromium
python3 dashboard/tests/layout_check.py --url http://127.0.0.1:8090
python3 dashboard/tests/layout_check.py --url http://127.0.0.1:8090 --source bhm
python3 dashboard/tests/layout_check.py --url http://127.0.0.1:8090 --source proofing
python3 dashboard/tests/layout_check.py --url http://127.0.0.1:8090 --source kc
python3 dashboard/tests/layout_check.py --url http://127.0.0.1:8090 --source gantt
```

Код возврата 1, если что-то поехало. Сплошной прогон нужен потому, что поломка
часто прячется **между** типовыми разрешениями: значение «1 435,6 шт/ч»
переносилось только на 1200–1280px, а на 390px и 1440px всё было в порядке.

Адаптер БХМ (вес партии считается один раз, пропуски и отмены не попадают,
часовой пояс) проверяется без зависимостей: `python3 dashboard/tests/test_bhm_source.py`.

Раздел расстойки — `python3 dashboard/tests/test_proofing.py` (или `pytest dashboard/tests`):
нормализация API, выпуск без двойного счёта, длительности и шт/ч, отменённые и
незакрытые партии, фильтры и часовой пояс, загрузка без двойного счёта, отказ API
(ФК и БХМ при этом работают), прокси фото без утечки ключа, Excel/PDF с теми же
фильтрами, неизменность ФК и БХМ. Поддельный бот поднимается локально, сеть не нужна.

Раздел КЦ — `python3 dashboard/tests/test_kc.py`: контракт API бота и ключ, открытые/завершённые/
отменённые, чел·ч и выработка (Σ/Σ), нет ложного «готового выпуска», группировка «продукция +
операция», смены и полночь, период по времени завершения, сотрудники без выдуманного
распределения, остановки, Excel/PDF с теми же фильтрами, отказ API КЦ без падения остальных
разделов и неизменность ФК, БХМ и расстойки.

## Если что-то не так

| Симптом | Куда смотреть |
|---------|--------------|
| `docker compose logs` пишет `DATABASE_URL is not set` | не заполнен `.env` или он не подхватился (`env_file: .env`) |
| `OperationalError: connection refused` / таймаут | ВМ не видит базу: файрвол на стороне Relax Dev, неверный хост/порт → пробуй `SOURCE_MODE=api` |
| `password authentication failed` | неверный логин/пароль в `DATABASE_URL` |
| `bot API rejected the key (401)` | `BOT_API_KEY` не совпадает с `DASHBOARD_API_KEY` бота |
| В логе `startup options rejected by the server` | нормально: база за пулером, сервис сам перешёл на `SET`, read-only сохранён |
| Страница есть, но пусто и жёлтый баннер | проверь `curl localhost:8090/health` на ВМ |
| Кнопка «Загрузить план» серая | не задан `PLAN_UPLOAD_TOKEN` в `.env` |
| «не нашлось ни одной строки с заполненным планом» | колонка «План количество» пустая во всём файле |
| План загрузился не на ту дату | в шаблоне `Дата план` — формула без сохранённого значения; выстави поле «Дата плана» перед загрузкой |
| Планы пропали после пересборки | нет тома `./data:/app/data` в `docker-compose.yml` |
| В PDF вместо кириллицы квадраты | в образе нет `fonts-dejavu-core`; пересобери с `--build` или задай `REPORT_FONT` |
| Выгрузка Excel скачивает не то, что на экране | файл строится по фильтрам из URL запроса — сверь лист «Фильтры» в книге |
| Процент выполнения подозрительно низкий | включён фильтр по сотруднику, смене или часу — план по ним не разрезается; смотри предупреждение над плитками |
| Файл перетащился, но ничего не произошло | зона загрузки серая — не задан `PLAN_UPLOAD_TOKEN`; причина отказа видна в журнале |
| Журнал загрузок пуст после пересборки | нет тома `./data:/app/data` — журнал лежит рядом с планами в `PLAN_FILE` |
| 502 от nginx | контейнер не поднялся: `docker compose ps`, `docker compose logs` |
| Кнопка «БХМ» серая | не задан `BHM_API_URL` в `.env` (или `BHM_SOURCE_MODE=off`) |
| `BHM API rejected the key (401)` | `BHM_API_KEY` не совпадает с `DASHBOARD_API_KEY` бота БХМ (или у бота он пуст) |
| `BHM_API_KEY is not set` | задан `BHM_API_URL`, но не задан ключ |
| `Cannot connect to host` на БХМ | ВМ дашборда не видит хост бота БХМ — проверь `curl` из раздела «Второй источник: БХМ» |
| Кнопка «Расстойка» серая | не задан `PROOFING_API_URL` (или `PROOFING_SOURCE_MODE=off`) |
| «API расстойки недоступно … (401)» | `PROOFING_API_KEY` ≠ `DASHBOARD_API_KEY` бота расстойки (не `ANALYTICS_KEY`!) |
| «API расстойки недоступно: Cannot connect to host» | бот расстойки не запущен или URL неверный — проверь `curl` из раздела «Третий источник» |
| Кнопка «КЦ» серая | не задан `KC_API_URL` (или `KC_SOURCE_MODE=off`) |
| «API кондитерского цеха недоступно … (401)» | `KC_API_KEY` ≠ `DASHBOARD_API_KEY` бота КЦ (не `ANALYTICS_KEY`!) |
| «API кондитерского цеха недоступно: Cannot connect to host» | бот КЦ не запущен или URL неверный — `curl` из раздела «Четвёртый источник» |
| Фото «не удалось загрузить» | бот не отдаёт `/api/dashboard/photo/{id}` (ключ, таймаут `PROOFING_PHOTO_TIMEOUT`) — подробности в логе дашборда |

## Закрыть доступ, если публичность передумаешь

Дашборд по умолчанию открыт всем, у кого есть ссылка. Закрыть — двумя строками в nginx
(закомментированные блоки лежат прямо в `nginx/fk-dashboard.conf`):

```bash
# по паролю
sudo apt-get install -y apache2-utils
sudo htpasswd -c /etc/nginx/.htpasswd fk
# добавить в server{}:  auth_basic "FK dashboard";  auth_basic_user_file /etc/nginx/.htpasswd;
sudo nginx -t && sudo systemctl reload nginx
```
